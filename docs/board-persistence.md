# Сохранение совместной доски

Доска отправляет атомарные действия (`add`, `upd`, `del`, `bg`), а не полную копию.
`edu_board_apply` блокирует строку доски, применяет действия к актуальному состоянию
и увеличивает `revision`. Разные объекты двух участников сохраняются вместе.
Одновременные правки одного объекта разрешаются порядком принятых сервером действий.
Удалённый объект не восстанавливается запоздавшим `upd`; отмена удаления — явный `add`.

Каждый запрос имеет устойчивый UUID. При потере ответа повтор с тем же UUID возвращает
текущее состояние и не применяет старые действия снова. Метаданные запросов находятся
в `edu_private.board_batches`, без клиентских привилегий и без доступа через Data API.
RLS без разрешающих политик здесь намеренно запрещает прямой доступ. Проверка Supabase
[RLS без политик](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)
носит информационный характер для этой закрытой таблицы.

Публичная RPC-функция выполняется как `SECURITY DEFINER`, потому что исходные таблицы
досок доступны напрямую только учителю. Она проверяет `auth.uid()`, принадлежность
доски, автора повторного запроса, допустимые действия и размер данных; `search_path`
пустой, имена квалифицированы, гостю вызов запрещён. Это намеренный API, проверенный
SQL-тестами, а не основание для отключения проверки
[привилегированных функций](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable).

Клиент хранит неотправленные действия и идентификатор запроса в localStorage.
Черновик разделён по аккаунту, доске и вкладке. Перезагрузка той же вкладки восстанавливает
очередь; запись подтверждённого запроса очищает только его действия. Ответ от уже закрытой
сессии доски не изменяет новое открытое полотно. Действия другого участника отображаются
через Realtime, но не выдаются за сохранённые до подтверждения его запроса.

Локальные черновики не заменяют серверную резервную копию: очищенные данные браузера,
закрытые без восстановления вкладки и другой компьютер не являются источником восстановления.
История полных состояний доски и интерфейс восстановления снимков — отдельная задача.

Лимит остаётся 3 МБ на состояние доски. Отклонённые запросы сохраняются как черновик;
ошибка проверки данных отличается от отсутствия сети. При переполнении/запрете localStorage
показывается просьба не закрывать страницу, без ложного обещания локального сохранения.

## Совместимость

Старый `edu_board_save` работает только до первого сохранения новым протоколом.
После этого полные устаревшие снимки отклоняются. Уже открытые вкладки перед совместной
работой нужно обновить; сначала дождаться завершения текущего сохранения.

## Проверки

- `node --test tests/board-sync.test.js`: 12 проверок очереди, задержек, повторов,
  ошибок сети/хранилища, вкладок, устаревших ответов и подтверждений Realtime.
- `tests/board-browser.js`: 11 сценариев реальной страницы в Chromium, две вкладки,
  рисование, текст, отмена, смена фона, перезагрузка и смена досок.
- `tests/board-persistence.sql`: 20 проверок настоящей базы с откатом фиктивных данных.
- Старые 17 проверок `tests/student-access.sql` также проходят после миграции.

Браузерная имитация сериализует записи Web Locks так же, как настоящая RPC сериализует
их блокировкой строки. Сам SQL проверяется отдельно в Supabase; имитация его не заменяет.

Проверка BOARD-UI-11 отключает доставку BroadcastChannel после успешного подключения: сохранённая запись учителя должна появиться у ученика через резервную сверку с сервером без перезагрузки.
